# الجزء الأول — القرارات الحاكمة

## ١ · لماذا نظام وليس سيرفر بريد

هذا السؤال يتكرر في كل اجتماع. الإجابة مكتوبة هنا لتُقرأ لا لتُعاد مناقشتها.

**سيرفر الإيميل يوصّل رسالة. نظام المراسلات يُنتج مستنداً رسمياً مرقَّماً.**

المكاتبة الرسمية تُراجَع **برقمها وسنتها** («صادر ٢٠٢٦/١٤١»). الإيميل لا رقم صادر له، ولا يوجد في بروتوكوله ما يُنتج واحداً.

| المطلوب | لماذا يسقط الإيميل |
|---|---|
| رقم صادر/وارد لكل جهة | لا يوجد. كتابته في الموضوع لا تمنع التكرار ولا تضمن التسلسل |
| إثبات الاستلام | «read receipt» يرفضه المستلم، ويختلف بالبرنامج، ولا وزن له. وهو ما يقوم به **دفتر التسليم** اليوم |
| الاعتماد قبل الإرسال | لا توجد حالة «قيد الاعتماد» في SMTP — الضغط على Send يُنهي الأمر |
| حالة المكاتبة | الإيميل يعرف «مقروء/غير مقروء» فقط |
| «أين تعطّلت وعند مَن» | مستحيل |
| الربط بالمقر | غير موجود |
| الأرشيف | سلاسل الردود المتداخلة أسوأ شكل لأرشيف قرارات تُراجَع بعد سنين |
| الحذف | المستخدم يمسح مستنداً رسمياً من صندوقه بلا أثر |
| QR والتحقق على الورق | مستحيل |

**السؤال الفاصل لأي جهة تسأل:** *«عند الخلاف على مكاتبة، كيف ترجعون إليها اليوم؟»*
«بالرقم من الدفتر» → يلزم نظام. «نبحث في الأوراق» → الإيميل يكفي.

**الشكل المعتمَد:** النظام هو سجل المكاتبات، **والتنبيه داخل النظام وحده — لا دور للبريد إطلاقاً** (قرار العميل 2026-08-19).
كل ما يخصّ الإخطار يحدث في الواجهة: بادچ عدّاد ثم جرس تنبيهات (الجزء الخامس). ⚠️ **لا SMTP ولا دومين ولا DNS ولا تكلفة** — وهذا يُغلق النقاش لا يؤجّله.

⚠️ **الفخ المرفوض:** «نستخدم الإيميل ونكتب الرقم في الموضوع» — انضباط يدوي بلا حارس، وأول يوم زحمة يُنتج رقمين متكررين لا يكتشفهما أحد.

## ٢ · القواعد التي لا تُكسر

هذه ليست تفضيلات — كسر أيٍّ منها يُفسد النظام بصمت:

| # | القاعدة | ماذا يحدث لو كُسرت |
|---|---|---|
| ١ | **`direction` ليس عموداً مخزَّناً** — «صادر/وارد» نسبة للمُشاهِد، تُشتَق من مقارنة جهة المستخدم بـ`from_entity_id` | المكاتبة تظهر خطأً عند أحد الطرفين |
| ٢ | **رقمان على كل مكاتبة — لكل جهة دفترها** | رقم واحد = ازدواج وفوضى في المراجعة |
| ٣ | **الرقم يتولّد لحظة الإرسال / لحظة الاستلام** لا قبلهما | مسودة مُلغاة تترك رقماً فارغاً وسط سجل رسمي |
| ٤ | **القراءة ≠ الاستلام** — `seen_at` واقعة، `acknowledged_at` إقرار رسمي | يضيع البديل الحقيقي لدفتر التسليم |
| ٥ | **المهلة على المستلم لا على المكاتبة** | لا يمكن معرفة مَن تحديداً تأخّر |
| ٦ | **«إرسال إلى» ≠ «نسخة إلى»** | يفسد سؤال «مَن لم يردّ» — صاحب النسخة غير مطالَب بالرد |
| ٧ | **الأرشفة والمفضلة شخصيتان** | أرشفة شخص واحد تُخفي المكاتبة عن الجميع |
| ٨ | **التفويض يضيف صلاحية ولا ينقل مسؤولية** — الإجراء يُسجَّل باسم النائب **مع الإشارة للأصيل** | تضيع المساءلة |
| ٩ | **نطاق الرؤية في `CorrespondenceScope::apply()` وحده** | التصدير يتجاوز نطاق الرؤية (درس `FeedbackScope`) |
| ١٠ | **الأصل لا يُكتب فوقه عند الختم** — المختوم مرفق جديد | يُفقد الأصل بلا رجعة |
| ١١ | **صفحة التحقق لا تعرض محتوى المكاتبة ولا مرفقاتها** | تسريب محتوى رسمي لأي حامل ورقة |
| ١٢ | **صورة التوقيع ليست توقيعاً إلكترونياً** — تُنسَخ ولا تُثبت عدم التعديل | ادّعاء حماية غير موجودة في سياق وزارة عدل |

📌 **قاعدة الاختبارات:** أي اختبار انحدار — اكسِر الكود عمداً وتأكّد أنه يسقط قبل اعتماده.

# الجزء الثاني — الوصف الوظيفي

## الفكرة
منظومة تبادل مستندات رسمية بين **رئاسة المصلحة** و**المكتب الفني لقطاع الشهر العقاري والتوثيق**:
قرارات وكتب دورية ومذكرات، بمرفقات ممسوحة ضوئياً، وإثبات استلام موثَّق بالوقت والشخص — بدل الورق والفاكس.

**فرع جديد** بنمط المخازن/الاجتماعات (`config/branches.php` + بنود sidebar).
الطرفان على المنظومة بحسابات — مؤكَّد من العميل (2026-08-10).

## المفاهيم

| المفهوم | التعريف |
|---|---|
| **المكاتبة** | المستند الرسمي: موضوع + محتوى + مرفقات + رقم + حالة |
| **الجهة** | رئاسة المصلحة / المكتب الفني (وقابلة للتوسّع بصف في قائمة) |
| **المستلم** | صف مستقل لكل شخص — **له رقم وارده وتاريخ استلامه ومهلته** |
| **التكليف** | مهمة مولودة من التحويل: عنوان + موعد أقصى + حالة |
| **المشاركة** | إطلاع شخص ليس مستلماً — **بلا نقل مسؤولية** |
| **التفويض** | نيابة مؤقتة بمدة محدَّدة تنتهي تلقائياً |
| **السلسلة** | الرد يرتبط بأصله عبر `parent_id` |

## دورة الحياة

```
        ┌──────── إرجاع للتعديل ────────┐
        ▼                               │
   [مسودة] ──إرسال للاعتماد──> [بانتظار الاعتماد] ──اعتماد وإرسال──> [مُرسَلة]
                                                                        │
                                                            ┌───────────┴───────────┐
                                                            ▼                       ▼
                                                    «تم الاستلام»            «إرجاع بسبب»
                                                            │                       │
                                                            ▼                       ▼
                                                      [مستلمة] ──رد──> [مردود عليها] ──> [مغلقة]
                                                                                [مرجَعة] → صندوق الراسل
```

**لحظتان حاسمتان:**
- **الاعتماد والإرسال** → يتولّد **رقم الصادر** ويُختَم اسم المعتمِد وتاريخه.
- **تأكيد الاستلام** → يتولّد **رقم الوارد** في دفتر جهة المستلم.

## مثال الأرقام الأربعة
مكاتبة واحدة من الرئاسة للمكتب الفني، والرد عليها:

| | الرئاسة | المكتب الفني |
|---|---|---|
| القرار | **صادر ٢٠٢٦/١٤١** | **وارد ٢٠٢٦/٨٩** |
| الرد | **وارد ٢٠٢٦/٢٠٥** | **صادر ٢٠٢٦/٣١٨** |

⚠️ لا علاقة بين ١٤١ و٣١٨ — **لكل جهة دفترها**، تماماً كالورق.

# الجزء الثالث — الجداول

## الأساس المشترك (يخدم المراسلات والشكاوى معاً)
```
attachments (polymorphic):
  id, attachable_type, attachable_id,
  path, original_name, mime, size(int), sha256(char64, nullable),
  uploaded_by(FK users, nullable), timestamps
  INDEX(attachable_type, attachable_id)

document_actions (polymorphic — سجل التداول):
  id, actionable_type, actionable_id,
  action(string),   ← الكتالوج الكامل أدناه
  status(string),   🆕 ← حالة المكاتبة **بعد** هذا الفعل
  from_user_id(FK users, nullable), to_user_id(FK users, nullable),
  on_behalf_of(FK users, nullable),      ← الأصيل عند التفويض (قاعدة ٨)
  from_user_name(string), to_user_name(string, nullable),   🆕 ← لقطة
  from_job_title(string, nullable),                          🆕 ← لقطة
  from_entity_id(FK correspondence_entities, nullable),      🆕
  notes(text, nullable), created_at
  INDEX(actionable_type, actionable_id)
```

### تتبّع المكاتبة — ثلاث قواعد تُبنى مع الجدول لا بعده

**١ · `status` عمود لا استنتاج.** استنباط الحالة من `action` ينكسر في موضعين: فعل لا يغيّر الحالة (`shared`, `stamped`, `viewed`)، وتغيير أسماء الحالات لاحقاً يجعل السجل القديم يُقرأ خطأً. العمود يجعل الخط الزمني يشرح نفسه.

**٢ · لقطة الاسم والمسمّى بجانب المفتاح.** المفاتيح `nullable`، فحذف موظف أو نقله يترك «—» مكان **مَن كانت عنده** — وهذا غير مقبول في سجل رسمي. والمسمّى تحديداً: خالد كان «رئيس القطاع» لحظة الاعتماد، وترقيته لاحقاً لا يجوز أن يُعيد كتابة ختم قديم. نفس مبدأ البوابة (`nullOnDelete` لحفظ التاريخ) لكن مع حفظ **النصّ** لا المفتاح وحده.

**٣ · السجل append-only.** لا `update` ولا `delete` ولا حذف تعاقبي مع المكاتبة (سلة المحذوفات لا تمسّه). سجل قابل للتعديل ليس دليلاً.

### كتالوج الأفعال — مقيس على خطوات الـexplainer
```
created · sent · approved 🆕 · rejected · received · viewed 🆕 · acknowledged
forwarded 🆕 · assigned · assignment_completed 🆕 · replied
linked_office 🆕 · shared · stamped · delegated 🆕 · closed · archived
```
⚠️ **الخمسة المعلَّمة 🆕 كانت غائبة، وخطوات في السيناريو المعروض على العميل تعتمد عليها**: «فتح المكاتبة وقراءتها» (خطوة ٥) · «ربط المكاتبة بمقر» (٧) · «إغلاق التكليف» (٩) · الاعتماد المنفصل عن الإرسال (٣) · التحويل الداخلي.
📌 **القاعدة: كل خطوة في الـexplainer لها فعل في الكتالوج.** الـexplainer وعدٌ للعميل، ونقصُ فعلٍ يعني خطوةً لا تظهر في السجل.

### ما يُشتَق بلا أعمدة إضافية
- **«عند مين الآن»** = `to_user_id` لآخر فعل حيازة (`sent`/`forwarded`/`assigned`).
- **«قعدت عند كلٍّ كم»** = الفرق بين طابعَي وقت متتاليين. وهذا ما يجيب عن **«مَن عطّلها»** — وهو السؤال التشغيلي الذي لا تجيبه قائمةُ أحداث بلا مدد.
- ⚠️ الاشتقاق يصحّ فقط إن كان السجل **كاملاً**: أي انتقال لا يُسجَّل يظهر كفراغ زمني يُحمَّل على الشخص الخطأ.

## القوائم المرجعية
```
correspondence_entities:
  id, name, code(string 8),   ← بادئة الرقم المعروض: «رئاسة ٢٠٢٦/١٤١»
  order(int), is_active(bool), timestamps
  seed: رئاسة المصلحة، المكتب الفني

correspondence_types:
  id, name, group(string, nullable),   ← عائلة النوع
  order(int), timestamps
  seed: [كتب ومذكرات] مذكرة · كتاب دوري   [قرارات وتعميمات] قرار · تعميم
        [أخرى] إحالة · طلب بيانات
```
> `code` جاء من ملاحظة مقيسة: النظامان التجاريان يستخدمان بادئة حرفية (`AFF_2024_1447`).
> وهي تحلّ خطر حقيقي: الجهتان قد تحملان الرقم ١٤١ في نفس السنة، والبادئة تمنع الخلط بصرياً.
>
> ⚠️ **الرمز تابع صاحب الدفتر لا المكاتبة** — فالمكاتبة الواحدة تحمل **رمزين**: «رئاسة ٢٠٢٦/١٤١» في صادر الراسل، و«فني ٢٠٢٦/٨٩» في وارد المستلم. ولذلك العمود على `correspondence_entities` لا على `correspondences`: الرقم يتولّد من (جهة + سنة) فالرمز يأتي من الجهة نفسها.
>
> ⚠️ **والرمز بادئة تُقرأ لحظياً لا قيمة محفوظة على المكاتبة** — فتغييره يُغيّر شكل الأرقام **الصادرة سابقاً**، فتخالف الورق المطبوع. وهذا يخالف روح قاعدة ٣ («الرقم لا يتكرر ولا يتغيّر»).
> **المطبَّق الآن:** تنبيه على حقل الرمز في شاشة التعديل وحدها.
> **المطلوب مع جدول `correspondences`:** **قفل الرمز** إذا كان للطرف مكاتبات مرقَّمة فعلاً — لا يمكن تنفيذه قبل وجود الجدول الذي يُفحَص.

## الكيان الأساسي
```
correspondences:
  id,
  from_entity_id(FK correspondence_entities),
  type_id(FK correspondence_types, nullable),
  subject(string), body(text, nullable),
  outgoing_serial_no(int, nullable), outgoing_serial_year(smallint, nullable),
  ref_number(string, nullable), ref_date(date, nullable),   ← جهات خارج المنظومة فقط
  priority(enum: normal|urgent|immediate, default normal),
  status(enum: draft|pending_approval|sent|received|replied|rejected|closed, default draft),
  drafted_by(FK users, nullable),
  approved_by(FK users, nullable), approved_at(datetime, nullable),
  rejected_reason(text, nullable),
  parent_id(FK correspondences, nullable),
  office_id(FK offices, nullOnDelete, nullable),
  is_scan_only(bool, default false),
  verification_code(ulid, unique, nullable),
  created_by(FK users, nullable), timestamps, softDeletes
  UNIQUE(from_entity_id, outgoing_serial_year, outgoing_serial_no)
  INDEX(status), INDEX(created_at), INDEX(office_id)
```
⚠️ **لا عمود `direction`** (قاعدة ١).
🔄 **`due_at` حُذف من هنا** ونُقل إلى صف المستلم (قاعدة ٥).

## المستلمون
```
correspondence_recipients:
  id, correspondence_id(FK cascade), entity_id(FK correspondence_entities),
  user_id(FK users, nullable),
  recipient_type(enum: to|cc, default to),        🆕 إرسال إلى / نسخة إلى
  incoming_serial_no(int, nullable), incoming_serial_year(smallint, nullable),
  needs_reply(bool, default false),               🆕
  reply_due_at(date, nullable),                   🆕 مهلة الرد لهذا المستلم
  seen_at(datetime, nullable),                    ← قرأ
  acknowledged_at(datetime, nullable),            ← «تم الاستلام» الصريح
  replied_at(datetime, nullable),                 🆕
  timestamps
  UNIQUE(correspondence_id, user_id)
  UNIQUE(entity_id, incoming_serial_year, incoming_serial_no)
```
> **هذا الجدول هو قلب الموديول.** كل مستلم له رقم وارده ومهلته وحالته — ولهذا هو جدول لا عمود.
> ⚠️ `cc` **لا يُطالَب برد ولا يدخل في حساب التأخير** إطلاقاً.

## التكليفات 🆕
```
correspondence_assignments:
  id,
  correspondence_id(FK cascade),
  recipient_id(FK correspondence_recipients, nullable),
  assigned_to(FK users), assigned_by(FK users),
  title(string), due_at(date, nullable),
  status(enum: open|done, default open),
  completed_at(datetime, nullable),
  timestamps
  INDEX(assigned_to, status)
```
> **التكليف يُنشأ من داخل التحويل** — عند إضافة مستلم يظهر مفتاحان مستقلان: «يحتاج إلى رد» و«إضافة تكليف»، لكل منهما موعده.
> ⚠️ هذا **يُلغي استبعادنا السابق** لـ«إدارة المهام»: التكليف هنا ليس موديولاً منفصلاً — هو ابن المكاتبة، وبدونه يبقى «طلب تحضير رد» بلا موعد ولا حالة.
> المهام المستقلة (بلا مكاتبة) **مؤجَّلة**.

## المشاركة 🆕
```
correspondence_shares:
  id, correspondence_id(FK cascade),
  shared_with(FK users), shared_by(FK users),
  note(string, nullable), created_at
  UNIQUE(correspondence_id, shared_with)
```
> إطلاع **للقراءة فقط** — لا يجعل المشارَك معه مستلماً ولا يعطيه رقم وارد ولا يُحمّله رداً.

## الحالة الشخصية (المفضلة والأرشفة) 🆕
```
correspondence_user_states:
  id, correspondence_id(FK cascade), user_id(FK users),
  is_favorite(bool, default false),
  archived_at(datetime, nullable),
  timestamps
  UNIQUE(correspondence_id, user_id)
```
> ⚠️ **قاعدة ٧:** الأرشفة والمفضلة **شخصيتان**. أرشفتي لا تُخفي المكاتبة عن غيري.
> لهذا هما في جدول لكل (مكاتبة، مستخدم) — لا عمودان على المكاتبة.

## التفويض
```
correspondence_delegations:
  id, from_user_id(FK users), to_user_id(FK users),
  starts_on(date), ends_on(date), reason(string, nullable),
  created_by(FK users, nullable), timestamps
  INDEX(from_user_id, starts_on, ends_on)
```
- المكاتبة تبقى باسم **الأصيل** — لا يُعاد تعيينها.
- النائب يراها في **تبويب «وارد الإنابة»** موسومة «بالنيابة عن فلان».
- إجراء النائب يُسجَّل باسمه **مع `on_behalf_of`** (قاعدة ٨).
- ينتهي بانتهاء المدة تلقائياً.

## تعديلات على جداول قائمة
```
users: + correspondence_entity_id(FK correspondence_entities, nullable)
       + job_title(string, nullable)        ← المسمّى الوظيفي المعروض 🆕
       + signature_path(string, nullable)   ← disk «local» لا «public»
```
> 🆕 **`job_title` — طلب العميل 2026-08-19.** ⚠️ **المسمّى الوظيفي ليس الدور**: خالد وياسر لهما **نفس الدور** (رئيس جهة) و**مسمّيان مختلفان** («رئيس القطاع» · «رئيس المكتب»). الدور حزمة صلاحيات، والمسمّى نصّ يُعرَض.

## ⚠️ الدفتر الورقي المتوازي — أخطر نقطة في الموديول
العميل أفاد (2026-08-10) أن **جزءاً فقط** من المراسلات سيمرّ على النظام، أي أن الدفتر يظل شغّالاً بالتوازي.
النظام لا يعلم أن الدفتر أخذ ١٤٢ يدوياً فيُصدره بدوره → **رقمان رسميان متطابقان**.

**الحل: وضعان يُضبطان من الإعدادات لكل جهة:**

| الوضع | متى | السلوك |
|---|---|---|
| **يدوي بتحقق** | الدفتر ما زال المرجع | الموظف يكتب الرقم، والنظام **يرفض المكرر** ويحذّر من الفجوات |
| **أوتوماتيك** | بعد وقف الدفتر | النظام يولّد الرقم كاملاً + خانة «ابدأ الترقيم من: ___» |

✅ **س٢ محسومة (2026-08-19): الدفتر الورقي مستمر — فالوضع اليدوي يُبنى، والوضعان معاً.**
`numbering_mode('manual'|'auto')` على `correspondence_entities`، افتراضه `manual`.

### ⚠️ الترقيم اليدوي يجعل قيد التكرار أخطر لا أهون
مع الأوتوماتيك يحمي القيد من التزامن أساساً. ومع اليدوي هو **الحاجز الوحيد** أمام خطأ كتابة — وما يُحسَب تكراراً يحدّده **س٦** وحده. والخطأ له اتجاهان، والثاني أسوأ:
- **قيد واسع** → تكرار حقيقي يمرّ، فيصير في السجل رقمان لمكاتبتين.
- **قيد ضيّق** → النظام **يرفض رقماً موجوداً فعلاً في الدفتر**. الموظف أمام ورقة مكتوب عليها ١٤١ والنظام يقول «مستخدم»، فلا مخرج له إلا اختلاق رقم آخر — **وهنا يفترق النظام عن الدفتر، وهو ما وُجد الموديول لمنعه.**

📌 **وفائدة عرضية:** مع اليدوي صارت إجابة س٦ **قابلة للمشاهدة** لا نظرية — **صورة صفحة واحدة من الدفتر تحسمها**: أرقام متتالية بأنواع مخلوطة = دفتر واحد؛ قسم مستقل لكل نوع = دفتر لكل نوع.

### ⚠️ سؤال جديد فتحه اليدوي — قبل الجدول لا بعده
**هل الرقم في الدفتر عدد صحيح دائماً؟** الدفاتر الورقية تستخدم «١٤١ مكرر» و«١٤١/أ» عند التصحيح. إن وُجدت هذه الصيغ فعمود `integer` لا يستوعبها، وتغيير نوع عمود على سجل مرقَّم هجرة خطيرة. **يُسأل مع س٦ في نفس الطلب** — كلاهما يُجاب من الصفحة نفسها.

⚠️ **توصية إدارية:** الازدواج مرحلة انتقالية، وكل ما طالت زاد التضارب. يُستحسن تحديد تاريخ لوقف الدفتر من البداية.

## خطوات شاشة الإنشاء
1. **نوع المستند** — مودال بالأنواع **مجمَّعة في عائلات** ثم «التالي».
2. **إرسال إلى** — كتابة الاسم، أو الاختيار من **المجموعات والمفضلة**.
3. لكل مستلم كرت بمفتاحين: **«يحتاج إلى رد»** (+ موعد) · **«إضافة تكليف»** (+ عنوان وموعد).
4. **نسخة إلى** — نفس الآلية، **بلا مطالبة برد**.
5. الموضوع (٥٠٠ حرف) + المحتوى.
6. المرفقات.
7. **حفظ المسودة** / **إرسال للاعتماد** / إلغاء.

## إجراءات الصف
عرض · تحويل · رد · **إرسال نسخة** · **مشاركة** · تعليق · تحميل · تصدير · **إنهاء** · **أرشفة** · **إرجاع بسبب** · حذف

## التنبيهات — داخل النظام وحده

**لا بريد، فالواجهة هي القناة الوحيدة** — لو لم ينبِّه النظام فلا شيء يُنبِّه. ولا بثّ لحظي (لا Reverb ولا Pusher في المشروع)، والتحديث يقع بطريقتين معاً:

| | الآلية |
|---|---|
| مع كل تنقّل | المشروع على `wire:navigate` فالعدّاد يُحسَب في كل صفحة تُفتَح |
| للجالس على شاشة واحدة | `wire:poll.60s` على بند السايدبار — `count` واحد لا استعلام سجل |

**مرحلتان:**
1. **بادچ عدّاد على «الوارد»** (المرحلة ب) — «كم مكاتبة في واردي لم تُستلَم بعد». بلا جدول ولا حزمة.
2. **جرس بقائمة منسدلة** (بعد المرحلة د) — يحتاج جدول `notifications` + مقروء/غير مقروء. قيمته ليست في الوارد (له بند في السايدبار أصلاً) بل في **تجميع خمسة أحداث متفرّقة على شاشات مختلفة**: مكاتبة جديدة · تكليف جديد · مسودة بانتظار اعتمادك · مكاتبة مرجَعة · مهلة رد قاربت — والأخيرة **لا شاشة لها** فلا تظهر إلا في الجرس.

⚠️ قبل المرحلة د لا يوجد إلا نوع حدث واحد، فالجرس يكون قائمةً بصنف واحد — والبادچ يؤدّي الغرض كاملاً.
نصّ التنبيه يذكر **الجهة الراسلة والرقم**: «مكاتبة جديدة من رئاسة المصلحة — صادر ٢٠٢٦/١٤١ · عاجل».

## أطراف العمل وأدوارهم — ✅ أقرّها العميل 2026-08-19

**م. محمد عبدة:** «الأطراف تمام · مع إمكانية إضافة أطراف جديدة · وإمكانية تعديل اسم ووظيفة المستخدمين تحت كل طرف».

ثلاث نتائج من إقراره:
1. **إضافة أطراف جديدة** — مغطّاة بشاشة `Entities\*`. ولا تكسر الترقيم: `UNIQUE(from_entity_id, year, no)` يفتح دفتراً مستقلاً لكل جهة تلقائياً.
2. **`job_title` على `users`** — الجزء الثالث. المسمّى الوظيفي ليس الدور.
3. **عرض المستخدمين تحت كل طرف** — فلتر «الجهة» في `Users\Index` + عدد المستخدمين في صف الجهة. لا شاشة ثالثة.

ثلاثة أدوار لا أكثر — مأخوذة من أطراف العمل في `correspondence-explainer.html`:

| الصلاحية | سكرتارية | رئيس جهة | مفتش |
|---|---|---|---|
| | سمير · محمد | خالد · ياسر | هبة |
| `index` · `view` · `create` · `attachments` · `share` | ✅ | ✅ | ✅ |
| `export` | ✅ | ✅ | — |
| `assign` | — | ✅ | — |
| **`approve`** · **`stamp`** | ❌ | ✅ | ❌ بالتفويض وقتياً |
| `delegate` · `delete` | — | ✅ | — |
| `settings` | — | — | — (لمدير النظام) |

**خمسة قرارات تُقرأ ولا تُعاد مناقشتها:**

1. **الكود لا يُنشئ أدواراً — يُنشئ صلاحيات فقط.** الهجرة تسجّل الاثنتي عشرة وتربطها بـ`super-admin` و`admin` (نمط `2026_07_16_000012_assign_warehouse_permissions_to_roles`)، والعميل يركّب الدور من شاشة الأدوار بالاسم الذي يريده. ⚠️ الكود لا يفحص اسم دور إلا `super-admin` (١٢٧ موضعاً)، فاسم الدور لغة تنظيمية لا مفتاح تشغيل.
2. **«موظف الصادر» و«موظف الوارد» دور واحد: السكرتارية.** ما يفرّق سمير عن محمد هو **جهته** لا دوره — والجهة عمود على المستخدم.
3. **لا حاجة إلى `multi-role`.** الاعتماد صفة **رئيس الجهة**، ودور واحد يُسنَد لخالد وياسر معاً، و`correspondence_entity_id` هو ما يحدّد أي دفتر يوقّع كلٌّ منهما منه. ⚠️ يُستثنى: لو كان لدى الجهة عدة رؤساء وواحد فقط يعتمد → يلزم دور «معتمِد صادر» منفصل، وساعتها فقط يلزم multi-role. وهذا رهن **س١**.
4. **لا عمود `branch` على `roles`.** قاعدة السلّم تُنفَّذ بعمود `level` الموجود (لا يزيد عن دور واحد بمستوى > ١)، وقاعدة الفرع تُشتق من صلاحيات الدور. وتحقُّق يعتمد على أن المدير يتذكّر ملء حقل هو تحقُّق يفشل يوم الحاجة إليه.

### مفتاح الأقسام المشروطة: **عنوان التصاريح** لا اسم الصلاحية

المصدر هو التجميع القائم في `permissions-grid.blade.php` (خمسة عناوين بعد إضافة المراسلات):

| عنوان التصاريح | ما تحته | القسم الذي يظهر |
|---|---|---|
| **إدارة المقرات** | المحافظات · المقرات · السيارات المتنقلة · المطالبات | **مربّع المحافظات** |
| الاجتماعات · المخازن · إدارة النظام | — | لا قسم |
| **المراسلات** 🆕 | المراسلات | **الطرف + `job_title`** |

⚠️ **قاعدة «الصلاحية تبدأ بـ`offices.`» خاطئة في اتجاهين — والاثنان مُثبَتان من الأدوار الفعلية على السيرفر:**
- **تفوّت:** دور `Vehicles` صلاحياته `vehicles.*` وحدها بلا `offices.` — فلا يرى المحافظات وهو يحتاجها لاثني عشر تقرير سيارات (٣٧ ملفاً يقرأ `$user->governorates()`).
- **تصطاد خطأً:** `offices.settings` تبدأ بـ`offices.` لكنها تحت **إدارة النظام** ولا علاقة لها بمحافظة.

⚠️ **التجميع يُرفَع من الـblade إلى موضع مشترك** (config أو كلاس) تقرأه **شبكة الأدوار وفورم المستخدم معاً** — تعريفان منفصلان يفترقان مع أول تعديل (درس `FeedbackScope` و`bulkQuery()`).
📌 `correspondence.settings` تُوضَع تحت **إدارة النظام** مع إعدادات المقرات والمخازن، **ولا تُظهر حقل الطرف** — مدير النظام يدير قائمة الأطراف بلا أن ينتمي لطرف.
⚠️ **الاجتماعات ليست منطقة محافظات** — مُتحقَّق منه (`grep` على `app/Livewire/Meetings/` و`Meeting.php` لا يُرجع شيئاً).
5. **المفتش مكلَّف لا مستلم.** المكاتبة تصل السكرتارية (صف في `correspondence_recipients`)، والمفتش يدخل **بتكليف**، فلا رقم وارد له ولا مهلة رد عليه. وهذا يحدّد مَن يظهر في قائمة «إرسال إلى»: السكرتارية ورئيس الجهة، لا المفتشون.

6. **شاشة مستخدمين واحدة بأقسام مشروطة — لا شاشة منفصلة لموظفي المراسلات.** الشاشتان تكتبان في نفس جدول `users`، فأول شخص يعمل في الفرعين يصير له حسابان وتضيع المساءلة. والقسم يظهر بحسب أدوار المستخدم: **المحافظات** لمن دوره فيه `offices.*`/`vehicles.*`، و**الجهة** لمن دوره فيه `correspondence.*`. فحساب رئيس الجهة **خمسة حقول** ولا يرى مربّع المحافظات أصلاً — أبسط من حساب مفتش المقرات لا أعقد.
   ⚠️ **صورة التوقيع لا تُرفَع من شاشة الإدارة إطلاقاً** بل من الملف الشخصي لصاحبها (المرحلة و) — لو رفعها المدير لغيره لم تبقَ البصمة دليلاً على أن صاحبها ختم.

⚠️ **`level` مخزَّن على الدور وهو في الحقيقة صفة الشخص** (`$user->roles()->max('level')` في `Dashboard.php`). الاختصار سليم ما دام لكل مستخدم دور واحد. ولذلك: **أدوار الفروع كلها بمستوى ١**، والمستوى يُضبط من السلّم الإداري وحده (مفتش/مستشار/رئيس). ولو صار التحقُّق معقّداً يوماً، فوقتها يُنقَل `level` إلى `users` — لا قبله.

**نطاق الرؤية:** مكاتبات **جهته** + ما هو مستلم فيه شخصياً + **ما شورك فيه** + **وارد مَن فوّضه** (داخل المدة).
super-admin يرى الكل. ⚠️ **يُكتب في `CorrespondenceScope::apply()` وحده** (قاعدة ٩).

# الجزء السابع — المرفقات والختم والتحقق

## المرفقات
- disk `public` (نمط `OfficeMedia`)، والحذف يمسح الملف في `booted()`.
- أنواع مقبولة: `image/*` و`pdf` بحد أقصى للحجم.
- ⚠️ **الصور تُضغط عند الرفع** وتُحوَّل PDF للمستندات متعددة الصفحات — الصور الضوئية اليومية أسرع مسبب لتضخم التخزين، وهذا الموديول هو الذي سيبلغ بنا حدّ Object Storage المؤجَّل.
- التنزيل محكوم بـ`correspondence.attachments`، والتحميل يخرج **ZIP** عند تعدد المرفقات.

## الختم — `App\Services\DocumentStamper`
✅ **مُثبَت عملياً بلا حزمة جديدة**: `mpdf 8.3.1` يجرّ `setasign/fpdi 2.6.7` وفيه `\Mpdf\FpdiTrait`.
جُرِّب: استيراد PDF صفحتين + نص عربي + لصق توقيع PNG → التوقيع مرسوم **٤٥.٠٠ مم × ١٦.٨٨ مم**، والفحص يسقط عند إزالة السطر عمداً.

```php
DocumentStamper::stamp(string $pdfPath, array $lines, ?string $signaturePath, array $opts): string
```

| نوع الملف | الحالة |
|---|---|
| صور JPG/PNG | ✅ تُحوَّل PDF أولاً |
| PDF ≤ 1.4 | ✅ مباشر |
| **PDF 1.5+** | ⚠️ FPDI المجاني يرفضه — **السكانرات الحديثة تُخرج 1.5–1.7** |
| Word/Excel | خارج النطاق |

**الحل لـ1.5+:** Ghostscript على السيرفر يخفّض الإصدار قبل الاستيراد (أمر واحد، مجاني).

**الموضع:** (أ) موضع ثابت أسفل آخر صفحة · (ب) **صفحة تأشيرة مستقلة** — الأأمن قانونياً لأن الأصل لا يتغيّر. كلاهما في المرحلة الأولى. السحب والإفلات مؤجَّل.

**حماية تشغيلية لا تُضعَّف:**
1. صورة التوقيع على disk **`local`** — لا `public`.
2. الرسم **سيرفر-سايد بحت** — الصورة لا تصل المتصفح أبداً.
3. الختم بحساب **صاحب التوقيع نفسه فقط**.
4. **الأصل يُحفَظ** — المختوم مرفق جديد (قاعدة ١٠).
5. تسجيل `stamped` في `document_actions` + `activity_log`.

## QR والتحقق
- `verification_code` (ULID) يتولّد مع المكاتبة.
- الـQR يُطبع على المستند ويوصّل لـ`/verify/{code}` **على سيرفرنا**.
- مَن يريد التزوير سيضطر لتزوير الورقة والنظام معاً.

**لماذا QR لا hash؟** رقم تحقق الملف (SHA-256) يعمل ما دام الملف رقمياً، لكنه **يفشل مع دورة الطباعة والسكان**: نفس الورقة تُعطي رقمين مختلفين عند مسحها مرتين (مُجرَّب). فالتقسيم: المكاتبات الرقمية → hash (**مؤجَّل**)، والمطبوع → **QR**.

# الجزء الثامن — خطة التنفيذ

## مبدأ التقسيم

المراحل مقسَّمة على أربع قواعد، وكسر أيٍّ منها يُنتج «تقدُّماً» لا يمكن تسليمه:

1. **كل مرحلة تنتهي بشيء يُنشَر ويُستخدَم** — لا مرحلة تسلّم جدولاً بلا شاشة تقرأه، ولا شاشةً بلا بيانات تعرضها.
2. **كل مرحلة تنتهي باختباراتها خضراء** قبل `push`. الاختبار يُكتَب مع البند لا بعد المرحلة.
3. **ما لا يعتمد على إجابة العميل يُبنى فوراً** — الانتظار لا يُقدِّم شيئاً.
4. **ما يعتمد على إجابته يقف قبل أول سطر منه** — لا نبني على افتراض ثم نعيد الكتابة.

⚠️ **ترتيب المراحل هنا يخالف الترتيب السابق في نقطتين مقصودتين:**
- **`Entities\*` + `Types\*` انتقلتا من ب إلى أ** — قوائم مرجعية بحتة بنمط `OfficeTypes`، غير مرهونة بشيء، وبدونها لا توجد جهة ولا نوع تُنشأ عليهما مكاتبة. وهما ما يجعل المرحلة أ **قابلة للتسليم** بدلاً من هجرات بلا واجهة.
- **جدول `correspondence_assignments` ينشأ في ب** (لا في د) لأن مفتاح «إضافة تكليف» في شاشة الإنشاء يكتب فيه. **شاشة `Assignments` وحدها** تبقى في د.

## ⚠️ أسئلة معلّقة — ثلاثة منها تعطّل البناء

📌 **قاعدة الصياغة: اسأل عن الواقع الورقي لا عن النظام.** العميل يعرف إجراءه بدقة ولا يعرف «ماذا يجب أن يفعل النظام».

| # | السؤال | الافتراض المبنيّ عليه | أثر التغيير |
|---|---|---|---|
| **١** ⭐ | **مَن يمضي الصادر اليوم على الورق قبل خروجه؟** | الموظف يحضّر والرئيس يعتمد ويرسل | لو أي موظف يرسل مباشرة → تُحذف خطوة الاعتماد |
| **٢** ⭐ | **هل يستمر الدفتر الورقي؟ وما الذي يمرّ على النظام؟** | مرحلة انتقالية — الترقيم يقبل الوضعين | لو أُوقف الدفتر → أوتوماتيك بحت |
| **٦** ⭐ | **التسلسل واحد للجهة أم لكل نوع تسلسله؟** | تسلسل واحد لكل جهة | لو حسب النوع → `type_id` يدخل في مفتاح الترقيم والـ`UNIQUE` |
| ٣ | هل ترغب الرئاسة في إدارة حسابات موظفيها؟ | لا — مدير النظام يدير الجهتين | لا يعطّل — دور «مدير جهة» |
| ٤ | هل توجد مدة معيارية للرد؟ | لا — `reply_due_at` يدوي | لا يعطّل — تُحسب من النوع |
| ٥ | كم مكاتبة شهرياً وكم صفحة؟ | غير معروف | يحدد توقيت تفعيل Object Storage |
| **٧** 🆕 | **هل تحتاجون «إظهار عند القيادي»** (رفع المكاتبة لنظر القيادة بلا تحويلها)؟ | لا — غير مبنيّ | لو نعم → عمود + تبويب |
| **٨** 🆕 | **هل تحتاجون «المشاركة» بجانب «التحويل»؟** | نعم — مبنيّة في المرحلة هـ | لو لا → تُحذف الشاشة والجدول |

**الأسئلة ١ و٢ و٦ تخصّ كلها لحظة واحدة — الاعتماد والترقيم والإرسال.** إجابتها معاً تفتح الطريق للبناء كاملاً.

📌 **س١ إجابتها مبنيّة في `correspondence-explainer.html` كله**: سمير يُعِدّ، وخالد يعتمد ويُرسل. فلو أقرّ المسؤول سيناريو الـexplainer، تكون **س١ قد أُجيبت فعلاً وبوابة المرحلة ج مفتوحة** — ويبقى **س٦ وحده** يقف أمام جدول `correspondences`.

✅ **سؤال «مَن يقيّد الوارد» لا يُطرح** — الـexplainer يحسمه في الخطوة ٦: **السكرتارية** («تأكيد الاستلام وقيده بالوارد — أ. محمد») لا المفتش. وهو ما يجعل السكرتارية هي صف المستلم في `correspondence_recipients`.

# الجزء الحادي عشر — العلاقة بموديول الشكاوى

الموديولان **نفس الشكل**: مستند + مسار تداول + مرفقات + إثبات استلام.
الفرق: المراسلات مسارها حر، والشكاوى مسارها ثابت:

```
الموظف يسجّل ← المفتش يفحص ← المستشار يعتمد ← الموظف يرفع على المنظومة
                    ▲                    │
                    └── مُعادة بملاحظات ──┘
```

**يُبنى مرة واحدة ويخدم الاثنين:** `attachments` · `document_actions` · `DocumentStamper` · `Verify` · «الإرجاع بسبب» · «التفويض» · «الاعتماد».
والشكاوى تستفيد كذلك من **نظام المستويات القائم** (`roles.level`: 1=مفتش، 2=مستشار) لأن مسارها حرفياً level 1 → level 2.
